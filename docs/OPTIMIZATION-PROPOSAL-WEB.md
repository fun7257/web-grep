# Web 前端优化方案（只谈方案，不改产品行为）

> 给：产品、前端、后端同事一起看。  
> 范围：只谈 `apps/web`（以及它怎么调用 `/api`）。  
> **这一份是方案，不是改代码的 PR。** 文里说「建议删 / 建议抽」都是后续单独做；本 PR 只加这篇文档。  
> **不改** 搜索多条件 `andTerms` 的含义，也不改搜索接口的对上方式。

---

## 怎么读

- 每条都按同一套：现状 → 问题 → 建议 → 风险 → 是否要后端一起改。
- 优先级：
  - **P0**：改动小、收益大，或现在已经容易踩坑。
  - **P1**：值得做，但要多测，或要先跟后端对一下字段。
  - **以后再说**：大仓库 / 大包体积才疼，现在不必排期。
- 「是否依赖后端」写 **否**，表示前端自己就能做完、行为保持原样。  
  写 **是**，表示只能先对齐文档或 `packages/shared`，**不要前端先发明字段**。

---

## 现在页面怎么跟后端说话（白话）

浏览器里是一个单页：左边目录树，中间搜索和命中列表，右边看一行预览；点文件名会再弹出「看更大一段」。

| 用户在干什么 | 浏览器实际发什么 | 怎么停掉上一轮 |
| --- | --- | --- |
| 点搜索 / 回车 | `POST /api/search`，正文是 JSON；命中用 **SSE**（服务器一边找一边往下推，不是一次性打包） | 新搜索会先 `abort` 上一轮；点取消 / Esc 也是同一条线 |
| 展开目录 | `GET /api/tree?path=…`，一次只列一层 | 展开子目录会取消；**根目录那次不会真正取消**（见 P0-2） |
| 点一条命中 | **不再请求文件**，右边直接用搜索里带回来的那一行字 | 无 |
| 点树里的文件名 | 弹出层按「从第几行起、要多少行」去 `GET /api/file` | 关弹窗 / 换文件会取消首包；**往上翻、跳行没有取消**（见 P0-2） |
| 打开页面 / 登录 | 先问 `GET /api/auth/status`，再 `GET /api/meta`；登录走 `POST /api/auth/login` | 卸载页面会取消开机这两下 |
| 地址栏分享 | **不发接口**。条件编进 URL（`?q=&p=&…`），登录成功后读出来再搜一次 | 无 |

搜索多条件：界面上是多个输入框；真正发给后端的是「第一条当 `query`，后面几条放进 `andTerms`」。后端按「一条接一条过滤」理解。**不要改成以前那种把多条件拼成一条正则**（仓库里还留着旧拼法，见清理清单）。

鉴权：登录后的会话令牌放在浏览器本地（勾「记住」进长期存储，不勾关标签就丢）。之后每个 `/api` 请求顺带带上令牌头。`401` 弹登录；`403 FORBIDDEN_HOST` 不当成密码错。

## 建议先做的 5 件事（给不往下翻的人）

1. **把「发 JSON、读错误、判断取消」收成一套小工具。** 现在搜索、树、预览、登录各写一遍，`/api/meta` 还散落在登录逻辑里。不改接口，只少抄代码。
2. **补上漏掉的取消。** 搜索已经做得对；目录树根节点、弹窗里往后翻页 / 跳行，换条件后旧请求还可能回来改界面。
3. **删已经没人走的界面和样式。** 旧「浏览整文件」预览、旧一行一条结果组件、旧搜索芯片样式、一批从未显示的文案。用户看不到变化，代码会轻一截。
4. **大结果列表少刷整页。** 命中一条条推过来时，现在每来一条就整表重新分组。列表已经做了「只渲染看得见的行」，但分组计算还是全量。可以攒一小批再画，观感不变。
5. **文档和共享类型跟上真实接口。** 根目录 `DESIGN.md` 还在写已经不存在的 TypeScript 服务；`docs/API.md` 还在写「多条件编成一条正则」。树的排除规则、文件「从尾巴读」这些，前端已经在用，共享类型和文档没写全。**只对齐纸面，不改搜索语义。**

下面按优先级拆开写。

---

## P0：先做（快、收益大）

### P0-1 请求、错误、取消写三遍的问题

- **现状：** 搜索 / 树 / 文件 / 登录各自 `fetch`；错误解析函数放在搜索文件里，大家都去借；「这是不是用户取消」有的判断、有的不判断。`/api/meta` 直接写在登录钩子里，没有自己的客户端。
- **问题：** 以后改前缀、改令牌头、改 401 处理，容易漏一家；树和预览的失败提示也不一样（有的吞掉、有的只留空列表）。
- **建议：** 抽一个很小的「JSON 请求」助手（拼地址、带头、失败读 `{ code, message }`、成功再用共享类型核对）。把「是不是取消」做成一个函数。`/api/meta` 也走同一条路。**不要改请求路径、字段、状态码含义。**
- **风险：** 抽的时候如果顺手改了「失败时要不要提示」，会变成行为变化。第一刀只搬家，测试对照现有搜索流程用例。
- **是否依赖后端：** 否。

### P0-2 换条件后，旧的树 / 预览请求还可能改界面

- **现状：** 新搜索会取消旧搜索，这点是对的。展开某个文件夹也会取消。但「根目录列表」重试最多 16 次，每次新建一个取消开关却从不按；弹窗里往后翻、往上翻、跳到某一行，多数没带取消。
- **问题：** 改了时间范围或排除规则后，上一轮树数据可能晚到，把新树盖掉。弹窗已经换了文件，旧切片还可能拼进当前内容。
- **建议：** 根目录那次也保住同一个取消开关，卸载或条件变了就按掉。弹窗翻页 / 跳行同样带上；回来时若文件已经不是当前这个，丢掉结果（现在跳行已经有「路径对不上就丢」，把取消补齐即可）。
- **风险：** 取消判错会把正常加载当成失败。要区分「用户取消」和「真的 401 / 网络挂了」。根目录重试不要在已取消后还继续睡 250ms 再打。
- **是否依赖后端：** 否。后端已经按连接断开停活；前端把开关按下去即可。

### P0-3 删已经没人走的预览分支和旧结果行

- **现状：** 主界面有个「浏览路径」状态，只会被清空，从未被赋成真正路径。树上点文件名走的是弹窗，不是右边栏那套浏览预览。结果列表用的是分组 + 虚拟列表；旧的「一行一条、带路径头」组件还在文件里，线上列表不用它。
- **问题：** 后面的人容易改错入口；浏览预览若被重新接上，会一次画出所有行（没有只画看得见的），大文件会卡。样式和测试还在护着这些死分支。
- **建议：** 删浏览预览组件及其样式；删主界面里只用于清空的浏览路径状态。旧结果行组件本身可删，但**高亮那几个小函数要留下**（列表、预览、JSON/Markdown 都在用）。测试里「点树文件不应出现浏览预览」那几条改成「应出现弹窗」即可。
- **风险：** 若产品其实还想保留「右边栏直接打开文件」，删之前跟产品对一下。以当前代码和测试为准，这条路是故意不用的。
- **是否依赖后端：** 否。

### P0-4 搜索命中一条条来时，少做全量重算

- **现状：** 服务器一边推命中，前端每来一条就往状态里追加，并触发列表：按文件重新分组、排序、再交给「只渲染看得见的行」的虚拟列表。
- **问题：** 一万条量级时，**画出来的行不多**，但「分组 + 排序」每条都做一遍，打字和滚动会顿。这是算力浪费，不是接口慢。
- **建议：** 流式接收仍立刻收下数据（状态条数字可以继续变），界面分组用「每 30～50ms 或每 N 条刷一次」，最后一条 / 结束事件必须立刻刷齐。不要改命中字段，不要等全部结束才显示。
- **风险：** 刷得太稀，前几条会晚出一点点。要压在「人眼觉得还是在往下长」。已有搜索流程测试要继续绿，尤其是「先来命中再来错误，行还在」。
- **是否依赖后端：** 否。SSE 事件形状不动。

### P0-5 先把会误导同事的文档标清楚、列进清理

- **现状：** `DESIGN.md` 仍按「TypeScript + 另一套服务框架」写整站，组件名、登录方式、有没有目录树都和现在不符。`docs/API.md` 仍写多条件会被编成一条正则。README 和真实 Go 服务更接近。
- **问题：** 新同事按 `DESIGN.md` / API 第 3 节对接，会做出和线上相反的搜索。
- **建议：** 另开文档 PR：`DESIGN.md` 顶上加「已过时，以 README + `docs/API.md` + `packages/shared` 为准」，或整篇改成指向现状。`docs/API.md` 多条件一段改成「前端传 `query` + `andTerms`」。**本方案 PR 不改那些文件。**
- **风险：** 只改文档，无运行风险。不要在文档里顺手改接口含义。
- **是否依赖后端：** 文档可以前端先改；若后端认为 API 第 3 节还有别的读者，一起看一眼即可。

## P1：接着做

### P1-1 目录树：勾选和过滤时不要整棵拆掉重装

- **现状：** 树是递归节点，展开过的子树都留在页面上，没有「只画看得见的」。每个节点都吃到整份勾选列表。改排除规则时，根节点的 React key 带上了过滤条件，等于把已展开的树拆掉重拉。
- **问题：** 仓库一大、展开一层，勾一下复选框会从根刷到叶。改排除规则会丢掉用户已经点开的位置。
- **建议：** 勾选变化时不要改 key，只改「勾没勾」的计算。节点用 memo，勾选列表用路径集合，避免父级一改子级全刷。排除 / 时间条件变了再整树重拉（这是该重拉的）。虚拟化放到「以后再说」。
- **风险：** memo 依赖写漏，会出现「勾了但方块没变」。要补树的专项测试（现在几乎只靠整页流程测到树）。
- **是否依赖后端：** 否。

### P1-2 预览里的 JSON / Markdown 少做重复重活，重库晚点再加载

- **现状：** Markdown 预览会走「转 HTML → 消毒 → 标出搜索词」，有缓存。JSON 预览每次父组件一刷新就重新解析、重新上色。`marked`、`dompurify` 和虚拟列表库打进**同一个 JS 包**，没打开预览也要下载。生产大约一包 JS 五百多 KB（压过大约一百五十多 KB）。
- **建议：** JSON 预览按「这段文本 + 搜索词」缓存。Markdown / JSON / 消毒库改成点到格式化预览再加载。虚拟列表已经在用，留在主包即可。
- **风险：** 懒加载第一下点格式化会闪一下空状态，要有占位。消毒参数不能在拆包时改松。
- **是否依赖后端：** 否。

### P1-3 文案：能翻译的都走词条；用不到的词条删掉

- **现状：** 中英两套词条是对得上的。但分隔条提示、快捷键说明、部分预览按钮、树的无障碍标签，还写死在代码里（有的只有中文）。大约十几个词条从未被界面读到（旧芯片搜索、旧「返回文件列表」、旧令牌提示等）。
- **问题：** 切英文后，一部分还是中文；死词条让人以为功能还在。
- **建议：** 分隔条、快捷键、预览「点击复制」、树的展开按钮，补进词条。确认界面不用的词条从三份语言文件一起删。`index.html` 的语言属性跟随当前语言。
- **风险：** 删词条若其实还有动态拼接，类型会在编译期拦住（词条名是写死的）。快捷键弹窗从「中英挤一行」改成跟语言走，是展示变化，不是快捷键变化。
- **是否依赖后端：** 否。`meta.defaultLocale` 现在后端写死中文，前端也默认中文；若以后要跟服务器默认语言，再单独立项。

### P1-4 主页面状态拆开，避免「弹个提示整页重画」

- **现状：** 搜索条件、勾选、时间、分享条、弹窗、吐司，都堆在同一个大组件里。搜索框有「正在打的」和「上次提交的」两份；另外还有一份写在可变盒子里给高亮用。
- **问题：** 出一条吐司也会让树、列表、预览一起重算。两份条件 + 一份盒子，改搜索逻辑时容易改漏。
- **建议：** 按「搜索提交」「树勾选 / 时间 / 排除」「分享 URL」「弹层」拆成几个钩子。盒子改成「提交时写一份不可变快照」，不要在搜索过程中原地改。**不改提交时组出来的请求体。**
- **风险：** 拆的时候最容易把「分享链接自动再搜一次」和「前进后退历史」弄乱。必须用现有超长搜索流程测试当护栏。
- **是否依赖后端：** 否。

### P1-5 查找和高亮两套「找词」合成一套

- **现状：** 列表高亮自己找词；预览里 Ctrl+F 又实现了一遍找词。转义正则特殊字符的小函数至少出现三处。
- **问题：** 正则 / 全词 / 大小写以后若要改规则，三处会对不齐，用户会觉得「列表黄了、预览里找不到」。
- **建议：** 共用一个「在这段文字里找这些词」的函数。预览查找只负责「在 DOM 里画框」，不要自己再实现找词。
- **风险：** 边界（空词、坏正则、中文）要沿用现有单测，不要「顺便优化」匹配规则。
- **是否依赖后端：** 否。命中里的 `matches` 下标含义不变。

### P1-6 登录框和其他弹窗走同一套壳

- **现状：** 分享、快捷键、看上下文，共用一个弹窗壳（点遮罩、Esc 关闭）。登录框自己画了一层遮罩，关法也不完全一样。
- **问题：** 无障碍和 Esc 行为两套；以后改遮罩样式要改两处。
- **建议：** 登录也套同一只壳。密码框、记住密码、错误提示保持现在的样子。
- **风险：** 登录失败时不要因为点到遮罩就关掉（现在登录关不掉是有意的）。套壳时把「点遮罩是否关闭」做成参数。
- **是否依赖后端：** 否。

### P1-7 预览每次拉多少行，跟共享上限用同一个数

- **现状：** 前端写死每次 160 行；共享包里已经有同一个数字。服务器回来的「预览上限」前端读了也不用。
- **问题：** 以后只改共享数字，前端不会跟走。
- **建议：** 前端改读共享包里的默认块大小。服务器若在 `meta` 里下发不同上限，再决定要不要跟——**跟之前必须和后端对过含义**，本条默认只改读共享默认值。
- **风险：** 误把「服务器允许的最大块」当成「每次请求块」，可能一次拉太多。先只统一默认 160。
- **是否依赖后端：** 只读共享默认值则否；若要用 `meta.limits` 则是，见第 6 节。

### P1-8 补测：树、弹窗翻页、取消，现在几乎只靠整页流程

- **现状：** 搜索主路径、分享链接、高亮、时间、勾选换算，单测不少。目录树节点、弹窗跳行 / 无限滚动、登录钩子、拖拽分栏，没有单独测。
- **问题：** P0-2、P1-1 这类改动，现在只能靠人手点，回归成本高。
- **建议：** 先加「根目录取消后结果丢弃」「弹窗换文件后旧切片丢弃」「勾选不拆树」三条。不必上浏览器端到端框架。
- **风险：** 低。测试会冻结当前取消语义，这是好事。
- **是否依赖后端：** 否。用假的 `fetch` 即可。

## 以后再说

### L-1 目录树只渲染看得见的节点

- **现状：** 展开多少就挂多少 DOM。
- **问题：** 某一层上千个文件时，即使用户只看十行，节点也全在。
- **建议：** 等真有「一层特别宽」的仓库再做窗口化。先做 P1-1。
- **风险：** 树有展开、勾选、缩进、懒加载，窗口化和「点名打开文件」容易打架。
- **是否依赖后端：** 否。一层最多约 2000 条是现成约定，先别改。

### L-2 外链字体改成本地或系统字体

- **现状：** 页面从 Google 拉三套字体。内网或禁外网时，字体会退回系统字体，布局一般还能用。
- **问题：** 第一次打开多一次外网；有的部署环境根本拉不到。
- **建议：** 需要离线 / 内网再改成本地字体或直接系统字体。
- **风险：** 换字体后字宽变化，分栏最小宽度可能要微调。
- **是否依赖后端：** 否。

### L-3 探测「服务活着」的健康接口

- **现状：** 前端从不打 `/api/health`，只靠 `/api/meta` 和搜索错误判断引擎在不在。
- **问题：** 健康接口对运维有用，对当前页没增量。
- **建议：** 不要为了「完整调用所有接口」去接。除非产品要做离线横幅。
- **风险：** 多一次公开请求。收益不明显。
- **是否依赖后端：** 接口已有；接不接是产品问题。

### L-4 前端过滤命中的开关

- **现状：** 搜索钩子留了「这条命中要不要留下」的参数，主界面从没传。
- **问题：** 多一套没人用的分支；若以后用它改 `done` 里的条数，会和服务器统计不一致（钩子里已经有改写条数的逻辑）。
- **建议：** 确认没有产品需求就删这个参数，避免有人拿它做「前端再滤一遍」。
- **风险：** 若有未合并分支在用，先搜全仓。
- **是否依赖后端：** 否。**不要**改服务器 `done.matchCount` 含义。

### L-5 树的「文件数」接口

- **现状：** 前端写了拉 `/api/count` 的函数，界面没有任何地方用。
- **问题：** 死接口封装，容易让人以为左边数字来自它（左边搜索次数来自 `meta` / 搜索流，不是文件数）。
- **建议：** 删封装；真要做「本目录多少文件」再写，并补共享类型（见第 6 节）。
- **风险：** 无，只要界面仍不用。
- **是否依赖后端：** 删前端死代码则否。

## 必须和后端对齐的事项（前端不要先发明）

下面这些是「纸面 / 共享类型」和「浏览器已经在发的」对不齐。  
**建议：先改 `packages/shared` + `docs/API.md`，Go 与 React 再跟着改。不要只在前端加字段。**  
**不建议、也不应在优化里改 `andTerms` 的语义。**

### B-1 目录树查询：排除规则前端已经在传，共享类型没写

- **现状：** 界面排除框会变成重复的 `exclude=` 打到 `/api/tree`（以及未使用的 `/api/count`）。Go 认这些参数。共享类型里的树查询只有 `path`、`mtimeAfter`。
- **问题：** 看起来像前端在发明参数；以后生成文档或校验查询串会漏掉排除。
- **建议：** 共享类型补上 `exclude`（以及 Go 已支持、前端暂未发的 `include`，若要写就标「可选、当前 UI 不发」）。`docs/API.md` 树接口补一行。前端继续发现在这些值，不改含义。
- **风险：** 补类型时不要改成必填，否则旧客户端缺参数会挂。
- **是否依赖后端：** **是**（共享包 + 文档；Go 行为应已具备，只需确认字段名就是 `exclude` / `include`）。

### B-2 文件预览：「从文件尾巴读」前端在用，共享类型没写

- **现状：** 弹窗跳行若没有那一行，会再请求 `tail=1`。Go 支持。共享的切片查询没有 `tail`。另有一份更老的「行号 + 上下各多少行」类型，前端预览已经不用。
- **问题：** 共享包同时存在新旧两套文件查询，读者不知道哪套算数。
- **建议：** 在现行切片查询上补可选 `tail`。老的「上下各多少行」类型是否删除，由后端确认没有其它调用方后再动。文档补 `tail` 和 `eof`。
- **风险：** 删老类型可能弄破共享包测试或外部脚本。先标废弃，再删。
- **是否依赖后端：** **是**。

### B-3 文件数接口没有共享响应类型

- **现状：** Go 有 `GET /api/count`。前端有一个手写「有没有 `count` 数字」的检查，界面未用。
- **问题：** 若以后接上，又会各写各的。
- **建议：** 要接线时再加共享类型。现在可以不接（见 L-5）。
- **风险：** 无。
- **是否依赖后端：** 若要补类型，**是**（只需加 schema，不必改 Go 行为）。

### B-4 `globAnd`（两套路径规则求交）界面永远传空

- **现状：** 共享类型和 Go 都支持 `globAnd`。提交搜索时前端写死空数组。树勾选走的是 `globInclude`，排除走 `globExclude`。
- **问题：** 这不是 bug。但文档若写成「勾选后再套包含规则会进 `globAnd`」，和现在不符。
- **建议：** 文档写清「当前 UI 不发 `globAnd`」。不要为了「用上字段」去改搜索范围——那是产品行为。
- **风险：** 有人若在优化里「顺便把包含规则改到 `globAnd`」，搜索范围会变。
- **是否依赖后端：** 文档对齐是；**改不改发送值要产品点头，本方案建议不动。**

### B-5 文档里的多条件搜索，还在描述已经不用的拼法

- **现状：** `docs/API.md` 写：多条件会被编成同一行的正则交替。真实前端走 `andTerms`。仓库里旧拼法函数还在，但主界面提交不用。
- **问题：** 后端若按文档再实现一遍旧拼法，会和现网不一致。
- **建议：** 改文档。旧拼法函数见清理清单，不要接回提交路径。
- **风险：** 只改文档则无。
- **是否依赖后端：** 文档建议前后端一起看一眼；**不要改 `andTerms` 契约。**

### B-6 SSE 本身：和现网是对齐的，不要另起炉灶

- **现状：** 事件是 `meta` → 过程中的 `progress` / `hit` → 最后恰好一个 `done` 或 `error`。心跳是注释行，前端会跳过。取消靠关掉这次 `fetch`，不是浏览器自带的 EventSource（因为要 POST + 带令牌）。
- **问题：** 优化时若改成 WebSocket / 改终态，两端都要改，收益小。
- **建议：** 保持。前端只修「流结束却没有终态」时的提示用词（现在是写死的英文 `search failed`），不要改事件名。
- **风险：** 无，只要不改协议。
- **是否依赖后端：** 协议不动则否。若有人在 Windows 代理上看到 SSE 帧拆不开，再一起查换行格式——那是联调项，不是先改契约。

### B-7 登录过期时间字段前端没用

- **现状：** 登录响应类型里有过期时间。产品约定是：会话不过期，直到退出或进程重启。
- **问题：** 无。不要前端自己做倒计时退出。
- **建议：** 保持忽略。若以后要过期，先改文档和 Go，再改前端。
- **风险：** 前端若自作主张按该字段踢登录，会变成行为变化。
- **是否依赖后端：** 维持现状则否。
